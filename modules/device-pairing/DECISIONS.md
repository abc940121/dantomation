# Decisions: device-pairing

Module-owned log. Append only, one line per decision with the reason. Trunk decisions are in the root DECISIONS.md.

- The `#t=` owner-token link is deprecated in favour of device pairing but not removed yet; the owner token keeps working until a later round removes it.
- Open: the pairing lockout is global (30 s after 5 bad guesses, for all clients), so one bad actor can briefly stop a legitimate pairing; per-source limiting is not done.
- A handoff child has its own 30-day sliding expiry and is NOT tied to its parent's: the parent is the browser tab nobody opens again once the home-screen icon exists, so tying the child to it would end the app after 30 days. Revoking the parent still ends the child at once (revoke writes both in one step, repeats repair a half-done revoke, and a child whose parent is missing or revoked does not authenticate). Pinned by a test: parent expired but not revoked, child still authenticates.
- A device made from any handoff (owner-minted or device-minted) carries handoff: true and cannot mint another handoff; a handoff redeem never resets the shared wrong-guess counter (only an ordinary pairing redeem or an ordinary owner mint does).
- The handoff feature first ships with the handoff: true marker on its codes and devices, so no handoff state without the marker exists and no migration is needed.
- The store lock is created with its content ({ pid, nonce }) already in it (a temp file linked into place). It is never taken from a live holder: a waiter gives up after 3 s and fails closed (busy), and a lock acquired after that point is released and refused. A holder is dead only when its pid no longer exists (process.kill(pid, 0) says ESRCH); anything else counts as live, so a reused pid keeps the store busy rather than risk a second writer. Manual way out: stop the server, then delete store.lock (and store.lock.reclaim if it is left over). A dead holder's lock is removed only under the exclusive file store.lock.reclaim, after re-reading that the lock is still the one seen dead. A lock that cannot be parsed fails closed. Both errors (busy, unreadable) carry the same way out in their text, without any path: stop the server, then remove store.lock and any leftover store.lock.reclaim in the state dir; the CLI adds the state dir on its own line and the server log gets the full line, while the HTTP reply stays generic. devices.json, pending.json and handoff.json are written only while holding the lock (seen.json, informational, is exempt), and write() acts only while the file still holds our nonce, so a holder that lost its lock cannot write back stale data (the caller refuses, 503 or throw).
A paired device may edit a group (PATCH /m/roles/groups/:id): rename it, add or remove members, archive it; nothing else (the route refuses any other field, journals first, and deletes nothing).
A paired device may also restore an archived group (PATCH /m/roles/groups/:id with {archived: false}, nothing else in the body) and read the list of archived groups (GET /m/roles/groups/archived): it can now read the names and member role ids of archived groups, with their archive time, and no persona, turns or other fields.
