# trace decisions

1. **New module, not an extension of spend-count.** spend-count is a `beforeTool` guard that reads a transcript; trace is event-driven and has state, routes and a panel. It needs no `ctx.api('spend-count')` (that api takes a transcript path, which task events do not carry), so there is no `dependsOn` and trace works with spend-count off. The price table in the config is the shared piece.
2. **Cost only from real usage.** Today `tool.done` has no `usage`; the module accepts it when core adds it and shows "cost unknown" (null) otherwise. No estimate from tool counts.
3. **File-per-task state with a lock**, as task-watchdog does: `tool.done` fires in the guard process, `task.start` in the harness process.
4. **Timeline events are capped** (`max_events_per_task`); extras are counted in `dropped_events`. Tool input is never stored.
5. **A resume continues the timeline**; elapsed time is wall clock from the first start, so time between a stop and a resume counts.
6. **A prediction is write-once** (409 on a second). The point is to commit before the work; rewriting afterwards would defeat it. It may be recorded before `task.start` (state "predicted"); the clock starts at the start.
7. **Overrun is checked on events, at task.end, by a 30 s job and by the list routes**, flagged once per task under the task lock.
8. **The alert goes to the line owner, not to a human.** `line_owner` is part of the event payload and the status line; no push notification is sent and nothing is cancelled. Other modules decide what to do with `trace.overrun`.
9. **Predict and result routes use `access: worker`** so a task can record its own prediction; reads are owner-only.
10. **Worker write scope (predict/result).** The core gives a worker route no task link: the worker token is one shared secret and the actor is `{kind:'worker'}` with an empty id, so a worker cannot be tied to the task it runs. Therefore results are owner-only (route access `owner`, handler also checks). A prediction stays write-once (409), and a worker may create one only for a task that has not started. SEAM REQUEST: if the core gives workers a distinct id (or a journal-verified task->worker claim visible in the route ctx), worker result writes can be re-enabled bound to the task's assigned worker.
11. **Un-started predictions are bounded.** They count toward `max_tracked_tasks` (pruned oldest first together with ended tasks), are dropped after 24 h without a start, and at most `max_unstarted_predictions` (default 100) may exist; more are refused with 429.
12. **Lock ownership.** The lock file holds a unique owner token and only that token's holder unlinks it. A lock older than 5 s is broken only while holding a breaker mutex (`<lock>.break`, created exclusively; one older than 10 s is cleared): the lock is re-read and unlinked only if byte-identical to what was judged stale. Acquiring is always an atomic exclusive create. The update never runs unlocked: on timeout (15 s) or an unexpected open error it throws; hook handlers catch at the boundary and journal `trace_skipped`, routes answer 503. Before the final state write the lock is re-read and must still hold our token.
13. **Pruning and the prediction cap take locks.** Pruning takes each task's lock and re-checks eligibility under it before unlinking. The `max_unstarted_predictions` count-and-create runs under one module-wide `predictions.lock` (taken before the per-task lock).
