# Decisions

Trunk decisions only (core, contract, server, security rounds). One line per decision, with the reason.

Layout: each module keeps its own log in `modules/<name>/DECISIONS.md` and `modules/<name>/PROVENANCE.md`, so a module branch never edits a root file (docs/module-contract.md). Early rows that were not clearly attributable to one module stay here.

- M1: one CLI, `taskmote`, with three verbs (`do`, `status`, `undo`). Fewer verbs means nothing to memorise; the agent picks its working method inside.
- M1: `do "<request>"` starts, `do` alone resumes, `do "<request>"` while a task is open refuses and says how to resume. One open task at a time matches the journal and the executor lock.
- M1: `taskmote do` runs `bin/harness.js start|resume` as a child process. The engine logic stays in one place; `harness.js` stays the low-level command.
- M1: `status` is its own summary (open task, last finished task, undo points, modules, warnings) and never prints the raw prompt, which `harness.js status` still does.
- M1: task method list (bug, change, review, unclear) goes in `config/protocol.md` as four short lines, because that file is always-on context. Written from scratch; no text taken from another project.
- M1: `unclear` means list the questions and stop, so an ambiguous request costs one message, not a wrong big change.
- M1: the review method asks for evidence (file:line or command output) and a second-model check when one is available, so findings can be verified.
- M1: `HARNESS_WORK_DIR` sets the base folder for task work dirs (default `work/`), so tests and Quickstart runs stay out of the repo.
- M1: the fake engine can send its mutating calls through the real guard hook, opt-in with `HARNESS_FAKE_GUARD=1`, so checkpoints are made by the same code path as with the real engine and the undo test needs no hand-made snapshots.
- M1: the Quickstart commands in README are extracted and run literally by `test/entry.js`, so the docs cannot drift from the CLI.
- M2: modules may export `priority` (lower runs first, default 0); approval-cards is 50 and checkpoint 90, so guard-base and private-rule hard blocks win over cards, and no snapshot is taken for a call that is only being held.
- M2: `onTaskStart` now runs before the prompt is built (bin/harness.js), so a module can journal a note the resumed agent sees. (Since S0 it is the `task.start` event, emitted after the `engine_start` record and still before the prompt is built.)
- S0: one manifest per module (modules/<name>/index.js) carries every extension point (hooks, commands, routes, panels, jobs, settings, runsOn), so a feature is a folder plus a config line and core never names a module.
- S0: `contract: 1` opts into strict validation (unknown fields are errors); a manifest without it is contract 0 and loads exactly as before, so existing modules and configs keep working while every new module is checked.
- S0: routes are mounted under /m/<name>/ by core, not chosen by the module, so two modules can never collide and a route always says which module owns it.
- S0: panels are browser ES modules under the module's ui/ folder with one entry point, mount(el, {base, fetch}) -> unmount, where fetch is the UI's authed fetch; the UI needs no knowledge of any module and static files need no build step.
- S0: jobs are declared, not started by the module: core owns start/stop (interval without overlap, or start -> stop function), so shutdown and the worker split stay in one place.
- S0: settings are a small typed schema (type, default, description, min/max, enum, items), checked against the config section named after the module; a bad key or type is a load error that fails closed like any module error, because a silently ignored setting is a wrong safety setting.
- S0: the settings validator is a few lines of plain Node, not JSON Schema, since no dependencies are allowed and the six types cover every current setting.
- S0: runsOn defaults to main; load takes a role so the pull worker (S3) reuses the same loader and skips main-only modules instead of having a second loader.
- S0: validation collects every problem of a manifest into one error line, so a contributor fixes them in one pass; the line still names the module first, as before.
- S0: the registry (lib/modules.js registry()) lists routes, panels, jobs, commands and settings and can match and call a route, but serves no HTTP; S1 adds the server on top without changing the contract.
- S0: the proof test hashes every core file before and after adding, using and removing a module, so "no core edits" is checked by a machine, not by review.
- S0 review: hooks, handlers, commands and routes may be async and core awaits them; beforeTool is cut off after modules_hook_timeout_ms (default 5000) as a module_timeout block, because a hung hook must never become a pass.
- S0 review: dependsOn is the only way to another module (ctx.api throws otherwise, a static test forbids require('../<other>')); a missing, off or cyclic dependency is a load error; load order is deps, then priority, then config order.
- S0 review: contract 1 replaces afterTool/onTaskStart/onTaskEnd with `on` events (task.start, task.end, tool.done) emitted after the journal write; a failing handler is reported and isolated; core owns task.*/tool.*, a module emits only under its name or a declared prefix.
- S0 review: ctx.state = {dir: state/m/<name>/ (lazy), append(record) tagged module: <name>}; checkpoint (state/ckpt) and voice (its flag file) are the documented exceptions.
- S0 review: secret settings are write-only, stored owner-only in state/secrets/<name>.json via `harness.js secret`, shown only as configured/missing; a secret inline in the config is a load error.
- S0 review: every in-repo module is contract 1; a contract-0 manifest still loads, with a printed warning. approval_cards.timeout_minutes has min 1.
- S0 v1.2: modules are trusted code in the harness process; dependsOn scopes ctx.api only and is not a sandbox. The doc says so, so nobody mistakes the contract for isolation.
- S0 v1.2: secret values reach a module only through ctx.secret(key); ctx.settings and every listing show configured/missing. Module error text is scrubbed of the module's secret values before it is printed or journaled.
- S0 v1.2: a throwing route returns a generic 500 with the id of a route_error journal record; the detail stays in the journal, never in the response.
- S0 v1.2: on Windows the secrets file gets inheritance cut, the owner granted and every other entry removed; a widened file is a warning on read (POSIX still refuses), because a lost secret is worse than a loud warning on a single-owner machine.
- S0 v1.2: route params are refused after decoding when they hold .., /,  or NUL; panel entries are resolved through symlinks and must be regular files inside the module folder.
- S0 v1.2: beforeTool may return only null, undefined, false or [kind, message]; anything else is a module_bad_result block, so a typo fails closed. Hooks get ctx.signal, aborted on timeout.
- S0 v1.2: job stop() runs in reverse load order and waits (timed) for an in-flight run; a service start is timed and a late start is stopped as soon as it settles.
- S0 v1.2: route access (owner default, worker, public-get) is declared by the module and enforced by core against ctx.actor; S1 maps its auth to the actor, so modules never check tokens.
- S0 v1.2: additive seams with no behaviour change for existing modules: provides {tools, bots, engines} + registry.providers(kind); prepareTurn context lines added to the engine prompt; ctx.tasks stub until S1; tool.done gains ok, durationMs and tool_use_id; settingsSchema/updateSettings for a settings UI (persisting the config is S1's save callback); stateVersion + migrate run once on load; uninstall hook + harness uninstall verb.
- S0 v1.2: the contract number stays 1: every new field is optional and every v1.1 manifest still loads unchanged.
- S1: the server (lib/server.js, node:http, no dependencies) keeps no state of its own: tasks, cards, worker jobs and the SSE stream are folds over the journal, so a killed server restarts into the same state with the same event seq numbers.
- S1: an event seq is (journal index + 1) * 64 + k, so it is stable across restarts and one journal record may yield up to 63 events; `since` replay is just a filter.
- S1: the server starts and resumes engines by running bin/harness.js (existing executor lock, journal, effect.js); it never edits task state except to journal a stop, so the one-open-task rule and idempotent effects still hold.
- S1: after a server kill the open task is reported stopped and is resumed explicitly (POST /api/tasks/:id/resume, or a card answer that clears its last pending card); a pre-act kill stays UNCERTAIN by effect.js design, a post-act kill is reconciled.
- S1: API tasks wait in a journal queue (queue_add) and the server starts them one at a time; bin/harness.js takes the id and bot from HARNESS_NEW_TASK_ID and HARNESS_BOT so the id returned to the client is the real task id.
- S1: only bots with runsOn "worker" produce job_queued records; worker jobs use separate record types and never become the open task, so they cannot block local work.
- S1: a claimed job carries a deadline (extended by each progress post); past it the server journals job_uncertain, the task is reported failed with uncertain true, and a late result is stored as job_late_result, never applied.
- S1: worker result is applied once per job id; repeats are acknowledged with applied false. A retried claim by the same worker returns its already-claimed job.
- S1: core never requires a module by name: the server takes undo, card store and applyAnswer from the loaded module objects (checkpoint exports undoStack, approval-cards exports cards and applyAnswer); with a module off its endpoints answer 404 or 409.
- S1: card answers share one function (applyAnswer) between the CLI and HTTP; unclear is journaled with the clipped text and returns 409 with the card still pending.
- S1: undo and status over HTTP run the existing CLI verbs in a child process with HARNESS_NO_SERVER=1, so the server and the direct path cannot diverge and cannot recurse.
- S1: the bearer token (server.token in the owner's state dir, created by serve if missing) is the real security boundary, because bots run on the same machine: every state-changing call and every worker route needs it even on loopback, so a bot cannot answer its own cards; server.local_no_auth (default on) relaxes read-only GETs only, and never for a browser Origin or Host from elsewhere.
- S1: the CLI finds a server through server.json in its own state dir and a live pid, so tests with a scratch state dir never reach a server elsewhere; HARNESS_NO_SERVER=1 forces the direct path; an unreachable server falls back to direct.
- S1: module routes mount under /m/<module>/ through the single provisional function listModuleRoutes() in lib/server.js; it returns nothing until S0's contract exists, and no contract shape is invented.
- S1: the token file is restricted to the owner (icacls on Windows, mode 600 elsewhere); if that fails the server still starts on loopback with a warning, but refuses to start on any non-loopback bind.
- S1: /api/events takes Authorization: Bearer like every route, so a page can read SSE through fetch streaming; module UI mounts under /ui/m/<module>/ (GET, relative assets, no trailing-slash redirect) through the single provisional listModuleUi() in lib/server.js. (Superseded by the S1-4 merge lines below: panels are at /m/<module>/ui/ via the registry.)
- S1-4 merge: module contract v1.2 wins every conflict; S1-S4 code adapted to it, none of lib/modules.js or the docs changed to fit them.
- S1-4 merge: the server loads modules through registry(cfg, {role, tasks}); routes under /m/<name>/ go through findRoute and callRoute with ctx.actor, and listModuleRoutes/listModuleUi are gone.
- S1-4 merge: panels are served at /m/<name>/ui/ from registry.uiFile (GET/HEAD only, symlink and path-escape checks kept); they are public static assets because a navigation cannot send a token and the files hold no data. chat-ui declares a panel with mount(el, {base, fetch}).
- S1-4 merge: the owner token maps to actor {kind:'owner'}; an optional state/worker.token (node bin/taskmote.js token new --worker) maps to {kind:'worker'} and may only call /api/worker/ and routes marked access: worker; a loopback GET with local_no_auth is anonymous. Everything state-changing still needs a token.
- S1-4 merge: ctx.tasks {enqueue, get, cancel} is filled by the server with the same code as the HTTP API; the registry reads it by reference, so it is a mutable object filled after the server's task functions exist.
- S1-4 merge: GET/PATCH /api/settings/<module> (owner only) returns the schema and values and saves through registry.updateSettings with an atomic config write (temp file, rename); secrets still go only through the secret verb.
- S1-4 merge: tool.done now really fires: bin/harness.js settingsFile() adds a PostToolUse hook running guard.js --after (the user's own Claude settings are never touched), and the guard journals a tool_done record (ok, durationMs, tool_use_id) before emitting the event; tested with the fake engine, which can run the generated hooks (HARNESS_FAKE_HOOKS=1).
- S1-4 merge: hook time budget: the timeouts that can run in one engine hook call must add up to less than the engine's 60 s; 60000 ms or more is a load error naming the modules and the total.
- S1-4 merge: the Windows widened-secrets-file check stays a warning but prints the exact icacls command for that file, built from the running account and the real path.
- S1-4 merge: fail-open crash closed: the module error formatter is total (a thrown null-prototype object reads as 'unprintable error') and guard.js blocks with exit 2 on any uncaught exception or unhandled rejection, so a crash can never read as an allow.
- S1-4 merge: route params are decoded once; a value that still holds a percent escape afterwards (%252e%252e%252f) matches no route, so a double-encoded traversal cannot reach a handler.
- S1-4 merge: route precedence: a literal segment beats a :param, compared per segment from the left at the first segment where the matching routes differ (then declaration order), so GET /admin is never shadowed by an earlier GET /:page.
- S1-4 merge: secret scrubbing also hides the JSON-escaped form of each secret (a newline inside a shown JSON value), and a secret shorter than 4 characters is refused at validation instead of silently not being scrubbed.
- S1-4 merge: ctx.state.append hides the module's secrets in every string of the record (nested too) before it is journaled; the plain redact clip is not applied, so records keep their full text.
- S1-4 merge: the Windows ACL check treats a whoami with no DOMAIN part as the machine's own account (the COMPUTERNAME env var plus the account name) rather than any domain's account with the same leaf name. Not covered by a test (needs a second account).
- Security round 2: the guard installs its fail-closed handlers before any require and always reports a non-empty config error (a thrown non-Error no longer fails open); state.append scrubs by JSON round trip (any depth, keys, Dates kept, unserializable refused); show() scrubs before clipping; hideSecrets goes longest-first and covers the double-escaped form; beforeTool block messages are scrubbed; isMe also accepts USERDOMAIN\user.
- Security round 3: block kinds and every module-produced error are scrubbed as a whole before they are split or clipped (a secret with a newline or a clipped prefix cannot survive); guard `die` emits a fixed reason, never exception text; route precedence is per segment from the left (a literal beats a :param at the first differing segment); `guard.js --after` always exits 0.
- Security round 4: route ctx can no longer override the sanitized params; load-time and uninstall-settings errors and event names in failure messages are scrubbed of the module's secrets; hideSecrets sorts every form of every secret together, longest first.
- Chat replies: after a local engine run the harness journals its final stream-json `result` text as a `reply` record (clipped to 4000), and the server sends it to the chat as a final `message`; before this the chat never showed what a local bot answered.
- Security round 5: the guard exits only 0 or 2 on PreToolUse (an exit-code wrapper turns any other code, such as the journal's 5, into 2), validates a non-array object input with a string tool_name and an object tool_input, defers its allow exit past pending timers/rejections and has an overall deadline that exits 2; every output sink (guard log/stderr, journal, errors, event names, the server, the reply journaled by bin/harness.js) is scrubbed against ALL loaded modules' secrets plus the owner/worker token values, and scrubbed BEFORE it is clipped; module load/setSecret/uninstall errors go through loadModule/loadWhy (a secrets file that cannot be read gives a fixed message); the reply parser reads only the bytes appended by this run. Not fixed on purpose: a module's synchronous busy-loop in beforeTool blocks the guard (modules are trusted code; no worker_threads isolation).
- Security round 6: the guard no longer forces its allow exit: it sets exitCode 0 and lets the loop drain, so a later throw/rejection of a hook (even 50 ms on) still reaches the fail-closed handlers, which are installed in --after mode too (fixed stderr text, exit 0); the overall deadline timer is unref'd and exits 2 if it fires (a module that leaves a live timer open is therefore blocked, by design); every enabled module's secrets are read before any module is loaded or validated, and every secret value ever read or set in the process (rotated-out ones too) stays in the scrub set; the harness hides the server.token / worker.token values before clipping a reply and scrubs before trimming. Out of scope: modules are trusted code and scrubbing is best-effort protection against ACCIDENTAL leaks of raw or once- or twice-JSON-escaped values; deliberate re-encoding (base64, a third JSON layer, splitting) is not defended.
- Worker replies: a worker task result now carries `reply` (the engine's final answer from the worker's own journal, scrubbed then clipped to 4000); the server shows it as the final chat message of that task instead of "done" (non-string ignored), so remote bots answer in the chat like local ones; replay derives it from the same job_result record.
- Known issue (open ticket): test/server.js "after restart the task is still known and not running" fails about 1 run in 20 (timing; seen before and after the reply changes, never reproduced on demand). Rerun once before treating it as a real failure; fix when it starts failing more often or a cause is found.
- Open: the commit-crash suite failed once inside `node test/run-all.js core` during the integration work and passed on rerun; treated as a timing flake and tracked, cause not found yet.
- Server: module jobs start in the main server once it is listening (`registry.startJobs`) and stop in `close()`, which now returns a promise that `serve` awaits before exiting. Without this a job such as chat-endpoint's `register` never ran under `serve`, so its rooms members always answered "unavailable". A job error is written to stderr and never stops the server. Only the main role starts jobs: the worker process builds a registry only for its policy modules (guard-base, guard-private-rules, checkpoint, worker), none of which declare jobs, so it does not start jobs.
- Voice: mac_client defaults ASR_URL/TTS_URL to a local mlx_audio server on 127.0.0.1:8011; env overrides unchanged, so a different port is one variable.
- Worker: setup.js check follows config worker.token_file like the worker does (config, then HARNESS_WORKER_TOKEN_FILE, then default); a missing, unreadable or empty file is a problem and the token, its prefix and length are never printed.
- Chat UI: a room select in the header (filled from the rooms list, hidden when the module is off) replaces editing the URL; ?room=<id> is read at start and kept in sync with replaceState, so a phone can bookmark a room.
- Server: readBody decodes with a fatal UTF-8 TextDecoder and answers 400 'body is not valid UTF-8 JSON' for invalid bytes, instead of storing U+FFFD from a non-UTF-8 shell.
- Worker setup: token and check share one token-path resolver (config worker.token_file, env, default); a malformed config is an error, a missing one is fine.
- Chat UI: ?room= is dropped only when a successful rooms list lacks it; a 401 or network failure keeps it.
- Cross-cutting decisions (more than one module) live one per file in docs/decisions/: voice-ownership.md, speaker-names.md. Rule: docs/module-contract.md.
